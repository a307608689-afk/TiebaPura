# 楼中楼宫格图实现

> 2026-09-20 ｜ 涉及版本：_client_version 12.64.1.1 → 22.11.1.0（仅 pb 详情族端点）
> 关联改动：楼中楼图片显示解锁 · 图片预览解耦 · 楼中楼引用头去冒号

## 一、需求背景

官方贴吧客户端已开放「楼中楼回复发送图片」，本工程需要：

1. 楼中楼回复的图片以宫格形式显示（不做发送功能）——详情页内联楼中楼预览、楼中楼详细页两处；
2. 图片预览解耦：帖子详细页打开图片左右滑**不会切进楼中楼图片**，楼中楼图片预览独立；
3. 楼中楼图片预览不设滑动范围，点开只看单张；
4. 主图预览的流式补页保留（滑到末尾继续拉后续楼层图，但不再混入楼中楼图）；
5. 楼中楼回复内容开头的冒号（`：`，服务端引用头残留）去除。

## 二、关键结论：显示链路本来就通，堵点在服务端版本门控

### 2.1 工程内显示链路（改动前已存在，零缺失）

```
pb/floor 响应
 └ SubPostList.content (field 2)
    └ decodePbContent                       ← 解码器解析全部图片字段（4 src / 6 bigSrc /
    │                                          8 cdnSrc / 9 bigCdnSrc / 25 originSrc / 36 cdnSrcActive）
    └ buildFragmentsFromPbContent           ← type 3/20 → ContentFragmentType.IMAGE + images[]
    └ mapSubPostComment → CommentItem.images
       └ ThreadDetail.CommentList / SubPostDetail 回复卡 ← ImageGrid 渲染分支早已存在
```

协议侧核实（n0099/tbclient.protobuf `SubReply.proto`）：楼中楼 `SubReply.content` 为
`repeated common.Content`，与主楼层 Post 的 content **完全同构**，协议天然支持图片片段。

### 2.2 根因：服务端按 `_client_version` 门控楼中楼图片下发

自研探测脚本 `tools/subpost_img_probe.js`（游客态直连，复刻 ProtoSchema 请求编码）实测：

| `_client_version` | 楼中楼 PIC 片段（type 3/20） | 图片表现 |
|---|---|---|
| 12.64.1.1 / 12.74.1.0 / 12.85.1.0 / 13.2.0.0 | **0** | 降级成 type=0 文本 `[图片]` 占位 |
| **22.11.1.0**（官方现行版，取自用户分享链接） | 正常下发 | 标准 tiebapic URL 四字段齐备 |

样本：tid=11037831637 六楼（pid=153951311576）楼中楼带图回复，12.x 下 `[图片]` 占位、22.x 下正常下发。

**注意两个取证陷阱**：

- 楼中楼回复里的「回复 @xx : …[图片]」文本是服务端拼的**引用文案**，不是图片降级证据；判据只看 type=3/20 片段；
- 升到 22.x 后 pb/page 预览路径的直回复 content 开头会多出一个独立的 `" : "` 文本片段（12.x 无），即「冒号问题」的来源（见 §五）。

### 2.3 修复方式：pb 详情族端点版本号升级

`TiebaService.ets` 新增常量（约 322 行）：

```typescript
const PB_CLIENT_VERSION: string = '22.11.1.0';
const PB_USER_AGENT: string = 'tieba/22.11.1.0';
```

**仅替换两处**（其余端点保持 12.64.1.1 不动，防未知回归）：

| 端点 | 函数 | 用途 |
|---|---|---|
| `/c/f/pb/page?cmd=302001` | `requestThreadPage` | 帖子详情（含内联楼中楼预览） |
| `/c/f/pb/floor?cmd=302002` | `fetchSubPostDetail` | 楼中楼详细页 |

`frs/page`（吧列表）等其它端点**不动**。22.x 响应结构经逐字段 deep 核对与 12.64 一致
（Post/SubPostList 字段分布无变化），回归风险收敛在内容侧。

> 连带影响：22.x 下楼层图 `cdnSrc` 档位从 `w=720` 变 `w=1080`，但工程取图逻辑
> `pickImageUrl`（按宽度参数最小择优）+ `rewriteUrlWidth`（重写省流档）会照常压回，
> 显示口径不变。

## 三、图片预览解耦

### 3.1 主图预览列表拆分（ThreadDetail）

`collectAllImages()` 去掉 comments 收集，只含主楼 + 楼层图片：

```typescript
private collectAllImages(): string[] {
  const all: string[] = [];
  if (this.detail && this.detail.images && this.detail.images.length > 0) {
    all.push(...this.detail.images);
  }
  for (const floor of this.floors) {
    if (floor.images && floor.images.length > 0) {
      all.push(...floor.images);
    }
  }
  return all;   // ← 不再收集 floor.comments[].images
}
```

### 3.2 ImagePreview 流式补页同步收口

`extractStreamImages()` 同步只收 `floor.images`——不改这里，补页会把楼中楼图又混回主图流，解耦不彻底。

### 3.3 楼中楼宫格单张预览

`ImageGrid` @Builder 增加第三参 `singlePreview`（默认 false，**调用点全部显式传参**，避开 @Builder 默认参数依赖）：

```typescript
ImageGrid(images: string[], capMaxWidth: boolean = true, singlePreview: boolean = false)
```

`singlePreview = true` 时（楼中楼宫格），点击仅传当前一张：

```typescript
if (singlePreview) {
  this.getUIContext().getRouter().pushUrl({
    url: 'pages/ImagePreview',
    params: { urls: [img] }        // 单元素 Swiper 天然不可滑；不带流式补页上下文
  })
  return;
}
// false：原「全局列表 + 流式补页」行为
```

调用点口径：

| 页面 | 调用点 | singlePreview |
|---|---|---|
| ThreadDetail | 主楼宫格 / 楼层宫格 | `false` |
| ThreadDetail | `CommentList` 楼中楼宫格 | `true` |
| SubPostDetail | 父楼层宫格 | `false` |
| SubPostDetail | 楼中楼回复宫格 | `true` |

SubPostDetail 的 `collectAllImages()` 同步只收父楼层图（父楼层宫格预览左右滑只在父楼层图内切换）。

## 四、楼中楼宫格图显示

显示侧零新代码——数据到位即点亮（渲染分支本就存在）：

- ThreadDetail `CommentList`：`comment.images` → `ImageGrid(comment.images, true, true)`；
- SubPostDetail 回复卡：`comment.images` → `ImageGrid(comment.images, false, true)`。

图片 URL 与主楼层同构，复用同一条取图链（`pickImageUrl` 择优 + `rewriteUrlWidth` 省流档）。

## 五、楼中楼引用头去冒号

### 5.1 冒号来源（22.x 两种服务端形态，探测取证）

| 形态 | 出现位置 | content 片段序列 |
|---|---|---|
| A：嵌套回复 | pb/floor 与 pb/page 均见 | `text"回复 "` + `type4 用户名` + `text" :正文"` |
| B：直回复 | **仅 22.x pb/page 预览**，每条都带（12.x 无此片段） | `text" : "` + 正文/图片 |

形态 B 的独立 `" : "` 片段单独渲染即屏幕上的孤冒号；纯图回复表现为「：」+ 宫格图。

### 5.2 实现：`stripQuoteColon(result: FragmentsResult)` 后处理

`TiebaService` 私有方法，两条楼中楼解析路径共用：

- pb 直连：`mapSubPostComment` → `buildFragmentsFromPbContent`（SubPostDetail / 父楼层）；
- modern 转换：`parseModernThreadDetail` 楼中楼映射 → `buildFragmentsFromContent`（ThreadDetail 内联预览）。

逻辑：

```
形态 A：首片段恰为「回复」/「回复 」→ 摘用户名后首个 TEXT 片段开头的 [:：]（连同前导空格，
        替换为一个空格维持间隔）；按片段原文 indexOf 定位，同步修正拼接 text（只动这一处，
        不用全局正则，避免误伤用户名/正文其它冒号）。
形态 B：无引用头且首 TEXT 片段 match ^\s*[:：] → 摘冒号；摘完只剩空白（独立" : "片段）
        则 frags.shift() 整片段移除；result.text 头部同步去冒号。
其余：原样返回（普通回复零改动）。
```

### 5.3 纯图回复渲染连带修复

纯图回复去冒号后 fragments 与 content 全空，会触发 `RichTextContent` 的「（无文字内容）」兜底。
两处楼中楼正文渲染改为**有片段或有文本才渲染**：

```typescript
if ((comment.fragments ?? []).length > 0 || (comment.content ?? '').length > 0) {
  this.RichTextContent(comment.fragments ?? [], comment.content || '（无文字内容）', ...)
}
```

纯图回复现在只显示宫格图。

### 5.4 已知边界

- 正文本身以冒号开头的回复会被误摘（罕见，接受）；
- SubPostDetail 消息通知定位的兜底匹配按 `notifyContent` 与 `comment.content` 全等比对，
  content 去冒号后会失配——主路径按评论 pid 精确匹配不受影响。

## 七、排障工具

`tools/subpost_img_probe.js`（tools/ 为打包排除目录，不随发布包分发）：

```text
node subpost_img_probe.js [client_version] [deep] [tid] [floor] [pid]
  client_version  默认 12.64.1.1；22.11.1.0 可验证图片下发
  deep            dump SubPostList 全字段号分布
  tid / floor     帖子 id / 目标楼层号（pb/floor 优先选该层）
  pid             直接指定楼层 pid：跳过 pb/page，直接拉楼中楼详情

示例：
node subpost_img_probe.js 22.11.1.0 x 11037831637 0 153951311576
```

判读要点：楼中楼图片下发看 content 里 `type=3/20` 片段及 4/6/8/9/25/36 号 URL 字段；
`[图片]` 文本与「回复 @xx : …[图片]」引用文案都不是图片数据。

> 注意：本机 shell PATH 无 node，使用 `E:\Software\DevEco Studio\tools\node\node.exe`；
> PowerShell 传空串参数会被吞导致位次偏移，占位用 `'x'`。
