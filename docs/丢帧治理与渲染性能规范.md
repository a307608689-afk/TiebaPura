## 1. 指标解读口径（先看懂数据再动手）

| 指标 | 含义 | 注意 |
|---|---|---|
| 每小时丢帧数 | 按页面累计的 vsync 未命中次数 / 页面使用小时 | **120Hz 设备上帧预算翻倍，同一卡顿会被记成约 2 倍**——本工程 `FrameRateBoost` 全局锁 120Hz，该指标天然虚高约 2 倍，看趋势、不看绝对值 |
| 卡顿影响设备数 | 发生过可感卡顿的设备去重数 | **真正反映问题的指标**，优先按它排优先级 |

2026-09-26 实测画像：受影响设备 TOP5 = Mate 80 Pro Max（SGT-AL10）/ Pura X Max 典藏版（HOP-AL10）/ MatePad Mini（MLR-AL00）/ Mate 80（VYG-AL00）/ Pura X View（VOL-AL00）——**全部是旗舰芯片 + 2.5K~2.8K 大屏 + 120Hz，无一台中低端机**。
结论：瓶颈是 **GPU 填充率（分辨率 × 像素量 × 每帧特效层数）**，不是芯片性能、不是 CPU/JS 逻辑。受影响页面 Top5 = Index / ThreadList / ThreadDetail / ImagePreview / Search，与「长时滚动页」重合。

## 2. 红线（禁止事项，改动前对照）

### R1 · 禁止在滚动内容容器上挂 `blendMode(..., OFFSCREEN)`

`.blendMode(SRC_OVER, OFFSCREEN)` 挂在列表/Scroll 内容层 = **整棵子树每帧先画进离屏 buffer 再合成回屏**，全屏级别的额外合成 + 带宽，在大屏高分辨率 + 120Hz 下是单项最大的每帧开销。
典型踩坑形态：内容层挂 `SRC_OVER+OFFSCREEN`，兄弟 overlay 挂 `linearGradient + DST_IN+OFFSCREEN` 做「渐显/渐隐带」（HomeTab/ThreadDetail/Search/MessagesTab/MineTab 曾全中招）。

**正确做法（渐隐/渐显一律用底色渐变 overlay，零离屏）**：

```ts
// 挂在内容层上的 overlay（替代 DST_IN 蒙版 + 容器 OFFSCREEN 的组合）：
// 内容滚入顶栏区域时被底色渐变覆盖淡出，视觉近似 alpha 渐显（顶栏磨砂下不可分辨）
@Builder
TopFadeOverlay() {
  Stack()
    .width('100%')
    .height(<带高>)
    .linearGradient({
      direction: GradientDirection.Bottom,
      colors: [
        [Theme.bg(this.isDark), 0.0],
        [this.isDark ? '#00101114' : '#00F2F4F7', <下沿比例>]   // 透明变体 = bg 色换 00 alpha 头
      ]
    })
    .hitTestBehavior(HitTestMode.None)
}
// 内容层不再挂任何 blendMode；透明色 '#00101114' / '#00F2F4F7' 必须与 Theme.bg 两档严格同值
```

注意：深浅两档透明变体是硬编码字符串，**若将来改 Theme.bg 的色值，必须同步改这些透明变体**（检索 `#00101114` / `#00F2F4F7`）。

### R2 · 120Hz 锁帧不得移除

`common/FrameRateBoost.ets`（`BOOST_ENABLED=true`，Index aboutToAppear acquire）是用户明确拍板的要求：**必须 120Hz**。任何性能优化不得以降帧率/卸锁帧为手段——正确方向是把每帧成本压进 8.3ms 预算（减离屏、减逐卡模糊层、减解码突发、减渲染树规模）。

### R3 · `autoResize` 在本项目禁用

百分比尺寸（`width('100%')` 遍地）下 `autoResize(true)` 解码失败且**不触发 onError**，表现为图格永久空白（2026-09-20 真机实证后全量回退，0 残留）。不要因性能理由再引入；解码减负走「CDN 预降档文件（w=720/360）+ 手动 createPixelMap desiredSize」路线，且必须真机单点验证后再铺开。

### R4 · 虚拟容器（WaterFlow/List 懒渲染）在「沉浸 + 双常驻槽位」页面禁用

历史 floor-vanish / GoodCategoryPage 21 轮教训：虚拟容器 item 测量在沉浸布局下不可靠。大内容页的减负手段用 **§3 渐进挂载**，不用虚拟化。

## 3. 强制模式（该场景必须这样做）

### M1 · 大内容全量渲染页 → 渐进挂载

Scroll + Column 全量渲染（楼层/列表）在长内容下首帧构建成本高、滚动期渲染树大。改法（参照 `ThreadDetail.ets` 的 `mountedFloorCount` 实现）：

1. `@State mountedCount` 只渲染数据**前缀**（`slice(0, mountedCount)`），分桶/列布局函数改为接收前缀列表参数；
2. 首屏挂 `INITIAL` 批（12），滚动距已挂载末尾 `AHEAD_VP`（1800）内按 `BATCH`（12）追加，推进逻辑挂在既有 `onScroll` 链上（`.onScroll` 只能挂一个，串联进现有 lambda）；
3. **定位/跳转前必须扩挂载**：`scrollToXxx` 里若目标项未进前缀，先 `mountUpTo(目标索引 + 批量)` 并返回 false 交给既有帧后重试兜底；
4. **数据整体替换时挂载量取 `max(旧值, INITIAL)`**：身份补水/后台刷新/切排序会整表重赋数据，重置回小值会让已滚深的视图塌掉跳屏；保留旧值只是多渲染若干卡片，安全。

### M2 · 图片预取档位纪律（ImagePreview / 大图浏览页）

- 当前图：基础档 + 高清档（闸门 priority=1 插队）；
- ±1 紧邻图：**只拉基础档**（HASH 归一缓存多数已本地），高清档等它成为当前图再拉（独立去重集）；
- +2 远邻图：**延迟 350ms（滑动停歇）**再拉基础档，翻页/退出清定时器；
- 依据：翻页动画期叠加 720/原图下载 + 解码突发是预览页丢帧主因；720 宽文件解码约 0.7MP 已小于所有目标机型屏幕像素宽，**不要再做「按屏幕宽降采样 720」**（无效且 `autoResize` 被禁，见 R3）。

### M3 · 新增性能手段必须真机单点验证后再铺开

autoResize 翻车教训：SDK 注释与真机行为可能不一致。任何渲染类 API（降采样、混合模式、绘制优化）先在单页/单组件验证，真机确认无回归（尤其「本地缓存图不显示」「占位 logo 上屏」两类历史症状）再推广。
