# v1.0.8 首页信息流掉帧问题和空白问题修复

> 目标设备：120Hz 高刷真机（单帧预算 8.33ms）
> 定位周期：2026-09-30（首页四轮打点 + 一轮 A/B 归因 → 容器迁移；随后吧主页同方案迁移、热门榜改造）
> 相关文档：[丢帧治理与渲染性能规范](./丢帧治理与渲染性能规范.md)、[floor-vanish-viewport-fix](./floor-vanish-viewport-fix.md)、[图片加载治理](./图片加载治理.md)

## 1. 问题现象

**首页「推荐」信息流**：

1. **滑动中周期性"顿一下"**，观感上内容会"抽搐"一下；
2. **深滑到很下面后再往上回滑，会出现一段空白**，继续往上滑卡片内容才恢复正常。

**吧主页（ThreadList）单列档**：同样存在滑动中的周期性抽搐（同一套"全量布局 + 窗口化挂载"实现）。

两个现象都出现在手机单列档，此前的实现是 `Scroll + Column 全量布局 + 窗口化挂载`
（`ForEach` 遍历全量 + 窗口内真卡 / 窗口外等高占位 + 滚动推进窗口）。

## 2. 诊断体系（本轮搭起来的真机打点）

| 打点 | 位置 | 含义 |
| --- | --- | --- |
| `FSTAT` | `common/PerfTrace.ets`（既有） | 每 2s 一行：`fps / max / d8 / d17 / d33 / d50 / d100` + `page/scroll/ev`（事件计数含 `win/img/swap`） |
| `HSLOT SLIDE` | `HomeTab.slotUpdateWindow` | 每次窗口推进：可见区 `vis`、窗口 `win→win`、新建 `mount` 张、携带图片 `imgs` 张、估算偏差 `errN/errAvg/errMax` |
| `HSLOT GAP` | 同上 | **可见区越出已挂载窗口**（视口内存在占位）= 空白问题的直接判据 |
| `HSLOT HEST` | `slotRecordHeight` | 单卡"占位估算高 vs 实测高"偏差 |
| `SLIDEGAP` | `onHomeScroll` 开头 | **推进帧真实耗时**：推进写 `@State` 后，下一次 `onScroll`（= 该帧渲染完成后的下一帧回调）与之的差值 |
| 渲染变体 A/B | `CommonComponents` | 普通模块变量（非响应式），按推进次数轮换：`0` 基线 / `1` 去胶囊 `backgroundBlurStyle` / `2` 图片区换等高灰块；只影响之后新建的卡，不触发既有卡重建 |
| `[FRS] HOT rank` | `TiebaService.fetchForumHotRank` | 热度榜聚合结果：`raw`（合并去重后）/`pinned`/`kept`/`filtered` |
| `[NETQ] img-flood` | 图片下载队列 | 每个窗口的图片请求 `total` / 并发 `peak` / 跨度 `span` |

分析脚本（工作区 `logs/`，不在工程仓库内）：`analyze.ps1`（打点汇总）、`correlate.ps1`
（每 2s 帧统计 × 推进量相关性）、`gap.ps1` / `gap2.ps1`（按变体、按新建张数分层）。

## 3. 诊断结论（四轮实测收敛）

### 3.1 第一轮：确认"一次推进 = 一帧冻结"

- `SLIDE` 时间戳与 `FSTAT` 的最差帧时刻**逐条吻合**（例：`SLIDE 01:22:26.160` ↔ `max=53 at=01:22:26.159`；`01:22:33.067` ↔ `max=64`）。
- `mount=8`、约每 0.6~0.9s 一次 → **6.5~9ms/张**，单帧冻结 50~75ms（120Hz 下掉 6~9 帧）。
- `GAP = 0`：窗口覆盖始终正确 → **空白与"漏挂载"无关**。
- 回滑段 `errN = 0`：占位高度全命中实测表 → **不是"卡高未测"**。

### 3.2 第二轮：只缩小单次推进量 → 更频繁，依然顿

把挂载缓冲 10 → 5。结果：`d50` 归零，但 `win` 从 `1~3 次/2s` 涨到 `11~52 次/2s`
（每秒十余次整列 diff + 重布局），体感仍顿。**说明"频次"与"单次量"是一个跷跷板，光调参数无解。**

### 3.3 第三轮：占位精度修复 → 空白消失、抽搐仍在

未实测卡的占位高由"单一 EMA 均值"改为「内容特征桶 + 结构公式」后：

- 估算偏差 `errAvg` 从 **80~120vp** 降到 **1~19vp**（`errMax` 285 → 44）；
- **空白消失**（视口上方不再发生高度重排把内容推走）；
- 但推进帧仍 30~40ms（`mount=6`）→ 抽搐仍在。

同时暴露一个关键相关性：

| 每 2s 窗口 | 最差帧 max | 推进次数 | 新建卡 | **高度修正卡数** |
| --- | --- | --- | --- | --- |
| max ≥ 40ms | — | 23.4 | 12.5 | **12.5** |
| 25~39ms | — | 32.4 | 16.7 | **12.4** |
| < 25ms | — | 25.8 | 13.9 | **3.1** |

高度修正是最强调节因子（12.5 vs 3.1）。

### 3.4 第四轮：A/B 归因 → 找到"与卡内容无关的固定代价"

按变体统计推进帧耗时，再**按新建卡数分层**（消除滑动速度混淆）：

| 新建卡数 | 基线 | 去模糊 | 去图片 |
| --- | --- | --- | --- |
| 1~3 张 | 21ms | — | — |
| 4~7 张 | 37.7ms | 34.3ms | 31.4ms |
| 13+ 张 | 73ms | — | 84ms |

**去模糊、去图片几乎不改变耗时**（同层差异仅 3~6ms，属噪声）→ 成本模型是：

```
推进帧耗时 ≈ 15~20ms（固定：整列重排/页面重渲染） + ~4.5ms/张（组件树构建 + 布局）
```

固定代价与"新建几张"无关，因此**在这个结构里无论怎么调窗口参数都必然掉帧**。

## 4. 修复

### 4.1 首页单列档容器改为 `WaterFlow('1fr') + LazyForEach`（根治）

依据：同页面多列档一直使用 `WaterFlow + LazyForEach`（虚拟化 + 节点复用），长期无卡顿反馈；
两者用的是同一套 `ThreadCard`。

- 落点：`pages/HomeTab.ets`
- 开关：`const HOME_SINGLE_USE_WATERFLOW: boolean = true`（**置 false 即一行回退**到原窗口化路径，
  两条路径都保留在 build 里）
- 配套三处必须同步，缺一会出问题：
  1. `homeColumnsTemplate()`：补 `n <= 1 → '1fr'`（否则单列会被铺成 3 列——与历史上"模板直绑 `this.columns`"的小窗 bug 同源）；
  2. `cachedCount` 下限抬到 5（单列时 1 个 FlowItem 就是一整屏）；
  3. `onHomeScroll` / 恢复滚动位置处的 `slotUpdateWindow(...)` 调用，与停歇预取的 `single` 几何判定，
     一律加 `!HOME_SINGLE_USE_WATERFLOW` 条件（WaterFlow 自管可见区，不许外部推进窗口）。

### 4.2 占位高度精确化（内容特征桶 + 结构公式）

（本项仍保留：原窗口化路径在 `HOME_SINGLE_USE_WATERFLOW=false` 回退时依然使用，且它是第三轮"空白消失"的直接原因。）

- 特征键：`图片数_标题行数_摘要行数`；
- 未实测卡：优先取同特征桶的实测均值（实测值回灌 EMA），缺样本用结构公式打底；
- 结构公式逐项复刻 `ThreadCard`：作者行 56 + 标题(8 + 行高×行数) + 摘要(6 + 行高×行数) +
  图片区（1 张 220；2/4 张两列 140/行；其余三列 100/行，行间 8vp）+ 吧标签 30 + 操作栏 62；
- 文本行数按 CJK 1 字宽 / 其余 0.55 字宽折算，clamp 到 `maxLines`；
- 实测卡高表容量 400 → 1200（长距离下滑后回滑仍命中实测值，避免退化到估算）。

### 4.3 吧主页单列档容器迁移（**与首页同方案**）

先做了一版"不动容器"的等价治理（窗口参数 4/9/15 + 特征桶估算），真机实测抽搐只是减轻、没有消失
（`win` 3~9 次/2s、`max` 31~61ms，仍是推进帧代价）→ 用户判定"仍会抽搐"，改为**直接采用首页同方案**。

`pages/ThreadList.ets`，开关：`const THREAD_LIST_SINGLE_WATERFLOW: boolean = true`（一行回退）。

**与首页方案的关键差异（勿混用、勿照抄）**：

1. **不挂 `WaterFlowSections`**：单列吧头本就全宽，作为**普通 FlowItem** 即可 —— 避开
   2026-09-24「跨 section 单列虚拟化真机整层不渲染」的既有结论（多列档仍必须走 sections，未动）；
2. **`rowsGap(0)`，卡距由卡片自身 `margin.bottom(6)` 承担** —— 让"置顶让位格"不产生间距（见下）；
3. **置顶仍是"合并卡片"**（一个 `bgCard` 内装「置顶」标签 + 全部置顶帖）：由数据源**首个置顶项**对应的格子
   渲染整块（`firstPinnedTid()`），**其余置顶项渲染 0 高让位** —— 从而在逐格虚拟容器里保住改造前的合并卡样式；
4. **尾部哨兵保留**（静默占位 / 加载中 / 加载失败点击重试三态），即吧主页**没有**丢首页那类尾卡提示；
5. 同时保留：吧头 + 兜底排序栏、`expandSafeArea` 沉浸、排序过场逐卡位移 + 快照锚点、左右滑切排序手势、
   下拉刷新、`onReachEnd` 加载更多；`onListScroll` 里的 `slotUpdateWindow` 调用加 `!THREAD_LIST_SINGLE_WATERFLOW` 条件。

真机结果：`win` 计数**全归零**，`max` 落回 14~33ms 区间（改造前 31~61ms），用户确认流畅、无空白。

### 4.4 「热门」档改为客户端热度榜（路线 1）

**动机**：贴吧 `frs/page` 只有 `sort_type 0`（按最后回复时间）/ `1`（按发帖时间）两档，而 UI 的「热门」档原先直接用 `0`
→ **与「最新·按回复时间」内容完全一致**（用户实测发现）。用户要求保留「按回复时间」，因此只能给「热门」换一个排序维度。

**方案**（`TiebaService.fetchForumHotRank` + 页面侧数据归属重构）：

- 并发抓 `HOT_RANK_PAGES = 2` 页 `sort_type 0`（第 1 页走 `fetchForumThreadsCoalesced`，命中"点击吧卡片即起跑的预取"省一个 RTT）；
- 合并去重（tid）→ **置顶保持前置**，其余按 `hotScore = 回复数 + 点赞数×2` 降序；
- 冷帖过滤：`hotScore < HOT_MIN_SCORE(6)` 且非精品剔除；过滤后不足 `HOT_MIN_KEEP(18)` 条则只排序不过滤（保底）；
- 榜单上屏上限 `HOT_RANK_CAP = 30`（原因见下"图片风暴"）；
- **不引入时间衰减**：`ThreadItem.createTime` 是展示串（"54 分钟前"），无法参与计算；
- 榜单之后的翻页继续按服务端时间序（`loadMore` 从 `HOT_RANK_PAGES+1` 页续接），浏览深度不受影响；
- 下拉刷新 / 静默刷新 / 切档预热（`warmupSort` 走 `key === 'hot'` 分支）/ 精选预取都按档位分别走对应数据源。

**数据归属分键（必做，否则缓存互相污染）**：新增 `sortKey()` = `'hot'` / `'0'` / `'1'` / `'2'`，
统一用于**列表缓存 key**（`forumCacheKey`）、**页内会话快照 key**（`sortSession`）、**上屏竞态判定**（`SortDisplay.key`）。
原实现直接用 `effectiveSort()` 数字，导致“热门(服务端 0)”与“最新·按回复时间(也是 0)”共用同一份缓存与快照 ——
这本身就是一个既有隐患，本次一并修掉。

**修掉的一个连带问题（图片风暴）**：首版聚合 3 页共 58 条一次上屏 → 卡片图片走"挂载即发"的直连下载
（该路径刻意不吃全局闸门）→ 真机实测 **`img-flood total=205 / peak=39`** → 被 CDN 限流、大批 `onError` →
**宫格整片显示空白**。收敛为「2 页聚合 + 榜单前 30 条上屏」后首屏图片量腰斩，该现象消失
（其它吧、以及新加载内容均正常）。

### 4.5 失效图不再留白（图位底色）

个别帖子的图片在服务端已失效：CDN 对失效图返回"长条灰阶/贴字占位图"，客户端 `isPlaceholderImage`
正确识别并**拒绝上屏**（否则宫格会整片变成贴吧 logo）→ `resolve` 返回 `''` → 进入阶梯重试
`[0, 2s, 8s, 30s]`（约 40s，为"新帖图 CDN 同步延迟可达 30s+"刻意保留）→ 这期间宫格既无本地图、
直连又拿不到真图，且**没有兜底底色** → 观感是"一片纯空白"。

修法（`CommonComponents.GridCellContent` 的 4 处宫格 Image）：加 `.backgroundColor(Theme.bg(isDarkMode()))`,
即一个"凹陷的图位"；重试成功自动被真图覆盖，40s 后自动整卡降级为"图片加载失败，点击查看"。
**识别依据**：日志里这几条 URL 只有 `ALL candidates failed`，既无 `candidate fail`（网络失败）
也无 `candidate exception`（异常）→ 说明每个候选返回的都是占位图被判定拦下。

## 7. 已知差异与待办

1. **差异**：首页单列档改用 `WaterFlow` 后，滑到底不再显示「正在加载更多…」尾卡提示（平板档一直如此）。
   经确认**不恢复**。吧主页的尾部三态哨兵**已保留**。
2. **待观察**：首页日志中出现一次孤立 **706ms** 异常帧（发生在 2s 内 44 张图片落地时，
   疑似批量 `setCachedImage` 触发的卡级重渲染）。用户未感知，未治理。
3. **待观察**：吧主页切排序/刷新那一下仍有 40~55ms 的帧，对应 `swap`（整表 `onDataReloaded` 重建全部可见卡），
   属 `syncSourceData` 的既有机制（非窗口推进），可后续改成 diff 友好路径。
4. **可选**：失效图目前会在卡片重建时反复走完整重试链（日志里同一 URL 10 分钟内失败 10 次），
   可加"会话级短期失效记忆"省掉重复请求 —— 需先厘清它与"新帖图 CDN 延迟"场景的 TTL 口径冲突。
5. **可选**：失效宫格改为"隐藏该格并重排宫格"（比"空图位"更干净）；单图支路也可补同样的底色。

## 8. 方法论沉淀

1. **先打点，再动手**：`SLIDE`（窗口推进）+ `GAP`（可见区越界）+ `HEST`（估算偏差）三个出口，
   就能把"抽搐/空白"这类主观描述变成可判定的数字；`GAP=0` 直接排掉了"漏挂载"这个最直觉的假设。
2. **测量"推进帧真实耗时"**：推进写 `@State` 后，用**下一次 `onScroll` 回调**与推进时刻的差值近似该帧成本——
   比每 2s 的 `FSTAT max` 更能逐次归因。
3. **A/B 必须控制变量**：变体轮换会让样本落在不同滑动速度段（新建张数差 3.6 倍），
   直接比均值会得出"去模糊/去图片有效"的错误结论；**按新建张数分层**后差异才现出原形（噪声级）。
4. **警惕"参数跷跷板"**：窗口化挂载的"单次量 vs 频率"是此消彼长的，
   当成本里存在与单次量无关的固定项时，调参永远无解——此时应怀疑结构。
5. **同一页面里已验证的路径优先**：同页多列档 `WaterFlow + LazyForEach` 长期没问题，
   而单列档却在被窗口化挂载拖着——把单列档"归并到已验证路径"比继续优化窗口化更划算。
6. **"首屏上屏条数"是图片链路的隐藏杠杆**：卡片图片走"挂载即发"的直连（不吃全局闸门），
   所以**一次上屏多少条 = 一次打多少并发**。榜单类功能尤其要按"N 条"设上限
   （本例 58 条 → 205 请求 / 峰值 39 → 被 CDN 限流 → 宫格空白）。
7. **区分"网络失败"与"内容失效"**：`candidate fail`/`candidate exception` 是网络层，
   `ALL candidates failed` 且两者皆无 = 每个候选都返回占位图被拦下 = **服务端内容已失效**；
   前者可重试救回，后者重试无意义，只能靠 UI 兜底（不留白）。
8. **虚拟容器的"不可用结论"要带条件**：吧主页当年"跨 section 单列虚拟化整层不渲染"的结论**成立**，
   但它只在"多 section"这个前提下成立——换成"单 section（无 sections）+ 单列模板"就绕过了该坑。
