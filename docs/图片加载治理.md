## 2. `ImageCache` 同步 IO 掉帧治理

原则：**只换等待方式与判定次数，不换任何语义** —— 命中 / 删除 / 落盘 / 占位识别的判据全部与改前一致。

### 2.1 Z1：`getVerifiedCachedPath()`（同步取「已确认安全」的缓存路径）

```ts
static getVerifiedCachedPath(url: string): string | null
```

- **与 `getCachedPath()` 的唯一差异**：额外要求文件大小 `≥ PLACEHOLDER_VALIDATE_SIZE`（`8000` 字节）。
  原因：小于该阈值的文件在 `resolve` 里还要过一次**像素灰阶校验**（贴吧非固定尺寸的黑白「贴字图」占位），
  同步路径无法等待解码，故这一档一律返回 `null` 交回异步流程。
- 因此判定范围是 `resolve` 现有语义的**子集**，不会比改前更容易显示占位图。
- 消费方：`CommonComponents.ets:454` 卡片组件创建时**整表一次性**预填本地路径（命中即首帧直接渲染真图，不等异步）。

### 2.2 Z2：写盘改异步

`fileIo.writeSync(file.fd, buf)` → `await fileIo.write(file.fd, buf)`。
字节内容与缓存文件名不变，只把等待方式换成 Promise —— 消除滑动中新卡进入时「整张图（100KB~1MB）同步写沙箱」占用主线程帧预算的问题。

### 2.3 Z3：`verifiedUrls` 校验通过集合

```ts
private static verifiedUrls: Set<string>   // 已完成完整占位校验（模板字节/尺寸/像素灰阶）的 URL
```

同一 URL 的缓存文件在「校验通过」之后内容不会变（重下会先删文件并清标记），
故 `resolve` 命中时**无需每次重复** `statSync` + `readSync` 整个文件 + 解码做灰阶校验。

**标记与 `memCache` 在所有失效路径上同步 `delete`**（文件被删 / 判为占位），不会单独失效。
写盘路径写入的字节刚通过完整校验，直接 `add` 为已校验。

### 2.4 Z4：灰阶校验按缩略尺寸解码

`isPlaceholderImage` 只判「**整图是否灰阶**」，结论取自采样占比（上限 512 点），与解码到原始尺寸无关。

- 改前：按原尺寸 `createPixelMap()`，再把 `total * 4` 字节（600×600 时约 1.4MB）整块拷进 `ArrayBuffer`；
- 改后：`createPixelMap({ desiredSize: { width: min(w,96), height: min(h,96) } })`，按解码后真实尺寸读像素；
- 采样步长与采样上限（512 点）口径不变；`getVerifiedCachedPath` 也补上了同一处 `verifiedUrls` 快路径（否则每次调用都要多走一次 `statSync`）。

### 2.5 缓存清理改异步

- **触发点 O(1) 化**：`pruneIfNeeded()` 只做计数 + 节流 + 互斥判定，不再在做判定时扫目录；
- **时间节流**：`PRUNE_MIN_GAP_MS = 5 分钟`，两次真实扫描最小间隔（`lastPruneAt`）；
- **互斥**：`pruneRunning` 防止并发重复扫描；
- **不 await**：`pruneAsync()` 全异步 IO（`listFile` / `stat` / `unlink`），跑完即止，绝不阻塞当前（很可能正在滑动中的）帧；
- **阈值与删除策略不变**：`MAX_CACHE_BYTES = 300MB` / `MAX_CACHE_FILES = 1500` / mtime 最旧优先。

### 2.6 图片调试日志总开关

```ts
static DEBUG_LOG_ENABLED: boolean = false;   // 默认关
```

`debugLog` 每次都做同步文件 IO（`statSync + openSync + writeSync + closeSync`），
而调用点遍布图片链路（`ImageCache` 内 17 处 + `ThreadCard` 12 处）→ 快速滑动每屏数十次主线程同步写盘，直接吃掉帧预算。
**排查图片问题**（模拟器上 hilog 被 SELinux 屏蔽时它曾是唯一通道）时**临时置 `true`** 即可恢复原日志。

## 4. §IMGQ：全局图片并发闸门（16 并发，FIFO + 视口门控入队）

```ts
// CommonComponents.ets —— 2026-09-19 由模块私有改为 export
const IMAGE_PRELOAD_CONCURRENCY: number = 16;   // v1.24：8 → 16（配合 §4.1 视口门控）
export function acquireImagePreloadSlot(): Promise<void>   // 满则入 FIFO 等待队列
export function releaseImagePreloadSlot(): void            // 交还槽位并唤醒队首
```

| 接入点 | 位置 | 说明 |
|---|---|---|
| 列表卡片 | `CommonComponents.ets`（`preloadImages`） | 原本就有的接入点（闸门诞生于此） |
| 详情页**楼层宫格 / 楼中楼宫格** | `ThreadDetail.ets` → `struct ThreadGridImage` → `attemptResolve()` | 楼层是**全量渲染**出来的（`Scroll` + `ForEach` 一次建出上百个本组件），此前**完全裸奔** |
| 详情页**头像** | `ThreadDetail.ets` → `struct AvatarImage` → `resolveGated()` | 楼层 + 楼中楼各有头像，29 楼一次性就是几十个并发 |

**效果**：下载按 FIFO 发放，表现为「楼层从上到下依次到图」，而非一次性百张并发。

> ⚠️ **闸门是 Promise 队列，必须 try/finally 配平**：`acquire` 成功后无论 `resolve` 抛不抛都要 `release`，
> 否则槽位泄漏 → 队列越排越长直至全部图片不加载。改动这一段逻辑时先看 `finally` 是否还在。

### 4.1 入队策略：详情页按视口门控（v1.24，修「比改造前更慢」）

**真机反馈**：「图片能正常加载了，但帖子详细页加载速度并没有提升，相反宫格图加载速度还比原来更慢了」。

**根因**：闸门限的是**并发**，没限**入队量**。

| | 列表页 | 详情页 |
|---|---|---|
| 渲染方式 | `WaterFlow` / `LazyForEach` **懒渲染** → 只创建可视卡 | `Scroll` + `ForEach` **全量渲染**（`floor-vanish` 修复的代价） |
| 后果 | 天然只下载「看得见的图」，队列永远很短 | 进帖瞬间上百个宫格 / 头像组件同时挂载并抢闸门 → 队列排到几十屏之后 → **首屏那 9~18 张也得干等** |

也就是说：**列表页靠懒渲染天然门控，详情页靠全量渲染全量下载**；改造前详情页是"上百张一起发、首屏很快就到"，
加了闸门后反而变成"首屏排在几十屏之后"。

**修法**：给详情页补上列表页天然具备的语义 —— **只下载看得见的内容**。

| 组件 | 触发点 |
|---|---|
| `ThreadGridImage`（楼层 / 楼中楼宫格） | `aboutToAppear` 只做 Z1 缓存同步命中；**`resolve`（落地缓存 / 自愈）改由 `.onVisibleAreaChange([0.0, 1.0], …)` 进入视口时触发**（`startResolve()` + `started` 一次性门闩） |
| `AvatarImage`（楼层 / 楼中楼头像） | 同款（头像数量与楼层同级，同样会占满槽位） |

- **门控只管 `resolve`**：直连（`directUrl`）在 `aboutToAppear` **挂载即发起**，不受门控 ——
  它才是"原版秒出图"的那条路（详见 §5.5）；
- 门控回调挂在**始终存在**的外层 `Stack` 上，不能挂在遮罩 / 灰底节点上 —— 撤遮罩会把门控节点一并摘掉，
  导致缓存永不落地；
- 触发过就**不取消**（滚过头仍继续下完），只是离屏图不再进 resolve 队列；
- **安全网**（`GRID_VISIBILITY_PROBE_FIRED` + `GRID_VISIBILITY_FALLBACK_MS = 1500`）：任一处回调触发即置位；
  若挂载 1.5s 后**没有任何**回调触发（说明可见性回调在本页环境里没生效），所有未发起 resolve 的图片退回
  「挂载即发起」的旧行为。首屏那几张必定最先触发，故正常路径下兜底永不生效。
  **注意：上屏速度不依赖这个回调**（直连不受门控），所以即使门控完全失效也不会出现"图不显示"。

| 项 | 效果 |
|---|---|
| 首屏 | 直连一次网络往返即上屏（§5.5）＋ 队列里只剩"看得见的图" → 16 并发一次到位 |
| 下方楼层 | 直连随挂载走（与改造前一致）；resolve 滚到才发 → 省流量 |
| 接口 | 会与接口争抢 rcp 会话的只有 `resolve`，其入队量从"上百张一次性"降到"一屏左右" |
| 流量 / 电量 | 没滚到的楼层至少省掉 `resolve` 那一路下载 |

> 后续若要再加"预取一屏"的前视能力，应从详情页既有的滚动预取（`DETAIL_PREFETCH_DISTANCE`）接入，
> **不要把门控取消** —— 门控一取消就回到"全量 resolve 入队、接口被拖慢"的老问题。

### 4.2 点击即预热（v1.26，P1）+ 按下即预取（P2）：把"秒加载"推进到页面打开之前

**现状盘点（数据侧已齐，无肉可吃）**：7 个列表入口全部挂了 `prefetchThreadDetail`（点击即预取详情数据，写入内存 + 磁盘缓存）；

**P1 点击即预热**：`prefetchThreadDetail` 成功后立刻调 `warmDetailPreviewImages(result)`：

**v1.27 追加（用户反馈「还能再快，网络好时基本无感」）—— 质变项：缓存 key 按图片 HASH 归一**：

- **问题**：列表卡与详情宫格对同一张图的 URL 形态不同（`wh%3D960…/sign=HASH.jpg` vs `w%3D580…` vs `/forum/pic/item/HASH.jpg`），
  整 URL 做缓存 key 时互不命中 → 「列表页刚看过的图」进帖仍要重新下载 —— 预热/直连做得再好也绕不开这一次网络；
- **修法**：`ImageCache.urlToFileName` 优先提取**图片 HASH**（`/sign=…/HASH.ext`、`/forum/pic/item/HASH.ext`、
  `/album/pic/item/HASH.ext` 三种形态）做文件名，同图所有形态落同一个文件 → **列表看过的图进帖直接本地秒出，
  与网络无关、跨重启有效**；提取不到 HASH（头像 himg、表情）回退整 URL hash，行为与改前一致；
- **连带**：`resolve` 的在途合流 key 改为**缓存文件名**（同图多变体并发下载会同时 TRUNC 写同一文件，必须共用任务）；
- **代价**：命中的可能是"更大尺寸的变体"（如 960px 源图渲染进 120vp 格），解码略重于专用缩略图 —— 换取零网络等待；
  真机若出现宫格解码卡顿，再给宫格 `Image` 加 `.sourceSize()` 按格解码；
- **预热扩批**：`warmDetailPreviewImages` 由"前 3 层"扩为两批 —— **首屏批**（主楼正文图 + 前 3 层，≤18 张）+
  **滚动批**（第 4~12 层，≤24 张），闸门 FIFO 天然让首屏排在滚动预热之前 → 往下滚也是本地秒出；
- **微调**：按下即预取计时 100 → 60ms（Move 判别仍在，不会造成滚动误预取）。

## 5. 首帧宫格图不显示修复（v1.22）

### 5.1 时序（为什么只在「首次进帖」且「加了闸门之后」必现）

| 时刻 | 控件侧（`Image` 回调，百毫秒级） | 数据侧（闸门后的 `ImageCache.resolve`，排队数秒） |
|---|---|---|
| t≈0 | — | `acquireImagePreloadSlot()` → 排队 |
| t≈200ms | 直连 CDN 失败 / 返回 200×200 防盗链占位 → 置 `fallbackTriggered = true`，启动重试链 | 仍在排队 |
| t≈2s | 重试链 tick → `attemptResolve()` **首行即被同一标记 return**（空转） | `resolve` 返回本地真图 |
| t≈2s+ | — | **结果被 `if (this.fallbackTriggered) return;` 丢弃** → `current` 停在灰色占位图 |

返回重进时 `aboutToAppear` 走 `getCachedPath` 命中 → 直接显示，所以「返回再进才正常」。
§IMGQ 把详情页纳入 8 并发闸门后，`resolve` 的排队时间被显著拉长，这条竞态从「偶发」变成「必然」。

### 5.2 修法：把「直连失败」与「放弃解析」拆成两个状态

| 字段 | 语义 | 谁写 |
|---|---|---|
| `directFailed` | **只表示「不能再指望直连」**（直连失败 / 200×200·238×238 占位），不再是放弃解析的闸刀 | `onError` / `onComplete` |
| `resolvedLocal` | **已落地本地真图 = 终态**，重试链与占位判定就此收工 | `attemptResolve` 成功时 |
| `resolving` | 解析在途，重试链不得重复占闸门槽位（否则同一张图在队列里排两次） | `attemptResolve` 进出 |

- `attemptResolve(thumb): Promise<boolean>` 改为**返回是否拿到本地真图**，重试链以这个布尔值为准（而不是去看控件侧标记）；
- 占位识别（保留直连原图，让 `Image` 自己触发 `onError` 进入重试节奏）改为 `if (!this.directFailed)`；
- `onComplete` 中「200×200 / 238×238 判占位」前先 `if (this.resolvedLocal) return;` —— 本地真图尺寸就是真实尺寸，
  **缩略图本身就可能正好是 200×200，会被误判**；
- `onError` 中若 `resolvedLocal` 为真则**解除终态**（本地文件损坏读不出时退回直连），避免死锁在灰底；
  重试链本身封顶两档（2s / 8s），不会因此兜圈。

### 5.3 可复用教训

1. **控件侧标记不得当数据侧的闸刀**：`Image.onError` / `onComplete` 是百毫秒级回调，而闸门后的解析是秒级排队 ——
   两者互为条件时，「先到的失败」会把「后到的成功」丢掉。**判断成功与否只看自己那条链的返回值**。
2. **「失败」与「放弃」是两个状态**：直连失败 ≠ 放弃解析。混用一个布尔量，一旦引入任何排队 / 延迟就会变成必然的丢弃。
3. **加并发闸门 = 把时序竞争放大**：任何「原本靠『解析比回调快』而侥幸正确」的代码，上闸门后都会暴露。
4. **本地终态要留解锁口**：`resolvedLocal` 是终态，但本地文件可能损坏 → `onError` 里必须能解回「灰底 + 重试」，否则死锁在灰底。

### 5.4 同源续修（v1.23，方案 A）：首帧不再直连 CDN，杜绝贴吧 logo 占位闪现

**现象**：图片已能正常加载，但**部分**宫格图会「先显示贴吧 logo，约几百毫秒后才变真图」。

**根因**：本组件首帧把 `resolveThumbUrl()` 得到的 **CDN 直连 URL** 当作 `Image` 的 src。
`Image` 走系统默认 UA、无 Referer/Cookie → 贴吧图床对这类请求返回 **HTTP 200 + 200×200 贴吧 logo 占位图**
（不是错误码，`onError` 不触发、被视作"加载成功"直接绘制）；真图要等 `ImageCache`（带移动端 UA + Referer + Cookie）
下完才替换 → 观感即 logo 闪一下再变真图。

> 工程里此前已规避过一版：`resolveThumbUrl()` 不再给 `/forum/pic/item/` 原图注入 `w%3D200`
> （注入后的非标准路径必然返回 logo，见 `ThreadDetail.ets` 该函数注释）。
> 剩余"部分"就是仍走直连、且受防盗链保护的路径。
> 列表卡片 `ThreadCard` 是同一套模式（`resolveImgUrl` 未命中回落 CDN URL），只是卡片小、滑动中不易察觉。

**修法（方案 A，已落地）**：宫格首帧**不向 CDN 发这个"必然拿到 logo"的请求**。

| 时机 | 现在（v1.23） | 以前 |
|---|---|---|
| `aboutToAppear` 命中本地缓存 | `ImageCache.getVerifiedCachedPath()`（Z1：含文件大小校验，语义是 `resolve` 的子集）→ 直接渲染真图 | `getCachedPath()` → 渲染真图 |
| `aboutToAppear` 未命中 | `current` 保持空 → 渲染**纯色块**（与 `Image.alt` 同色），只走 ImageCache 解析 | `current = CDN URL` → 先画上 logo |
| 解析成功 | `current = file://` 真图 | 同 |
| 解析失败 / 阶梯重试中 | 保持灰底（2s / 8s 两档继续重试） | 灰底 + 直连 logo 兜底 |
| 本地文件损坏（`Image.onError`） | `current = ''` 退回灰底 + 解除终态重试 | 回退 CDN 直连（引入 logo） |

- `directFailed` 字段与 `onComplete` 的「200×200 / 238×238 占位判定」**一并删除** —— 直连下线后不会再产生 CDN 占位事件；
- 纯色块颜色与 `Image.alt()` 完全同色 → 观感是**同一个灰底直接变真图**，不产生额外跳变；
- 几何（`width/height 100%` + `borderRadius(18)`）逐项复制，**布局零改动**。

**头像（`struct AvatarImage`）同源一并治理**（用户 2026-09-19「一起治」）：

- 首帧同样**不直连 CDN**：命中 `getVerifiedCachedPath` → 直接渲染真图；未命中 → `current` 保持空 →
  走本组件**既有的**「透明占位 + 外层首字母」分支（原本只有 `url` 为空时才走到），等 ImageCache 取回；
- `onError`（本地文件损坏）→ 退回首字母占位 + 允许**重解析一次**（`retried` 一次性护栏），不再回退 CDN 直连；
- 观感取舍：头像的创建顺序与视觉顺序一致，而闸门是 FIFO → **视口内**的头像基本即时到图；
  只有深层楼层（还没滚到的）会先显示首字母等排队，滚到时通常已就绪；
- 小文件注意：头像普遍小于 `PLACEHOLDER_VALIDATE_SIZE`（8000B），因此 `getVerifiedCachedPath` 对它们**恒为 `null`**
  （Z1 的语义是 `resolve` 的子集，小文件必须过像素校验）→ 已有缓存的小头像不走同步命中、仍走一次异步 `resolve`
  （命中缓存时无网络，仅文件读 + ≤96px 解码）→ 首字母最多闪一帧。

> 未纳入本次：`ThreadCard`（列表卡）里的 `authorAvatar` / `forumAvatar` 是**裸 `Image(url)` 直连**、既不走
> `ImageCache` 也不占闸门（40vp / 20vp 小图，真机未见 logo 反馈）→ 若将来也要治理，按同法接入即可。

**代价（已知并接受）**：首次进帖"未缓存"的图会先显示灰底，需等 8 并发闸门 + 下载完成；
已缓存的图（返回重进 / 二次进帖）零等待。等效于把「logo 闪现」换成「灰底等待」。

**未采用的备选**：B 保留直连做阶梯全失败后的最后兜底 + 撞占位立即退回灰底；C 放宽宫格并发；
D 按 host 记忆"直连必返占位"。
> **后续走向**：真机反馈"改造后明显变慢、没有了秒加载感" → **B 的思路在 v1.25 被改造采纳**（见 §5.5：
> 直连常驻 + 占位遮罩），因为它同时满足"不闪 logo"与"直连速度"。

### 5.5 直连 + 占位遮罩（v1.25，修「没有秒加载感」）

**真机反馈**：「还是提升不明显……之前进去虽然不算快，但宫格图基本秒加载的，现在有明显等待时间，没法做到秒加载的感觉」。

**根因（v1.23 的过度纠正）**：v1.23 为了消灭 logo 把直连**整条砍掉**，于是所有图都改成"等 `ImageCache.resolve` 下载 → 落盘 → 回读 file://"才上屏。
而原版"秒加载"靠的恰恰是**系统 `Image` 直连缩略图**（一次网络往返即解码上屏，且用的是系统自己的图像缓存）。
`resolve` 比直连多出：rcp 请求 → 占位校验解码 → 落盘 → 再读文件解码；再加进闸门排队 —— 快慢差距就在这几拍。

**修法**：**直连保留，但把直连结果盖在遮罩之下** —— 只有"确认为真图"才撤遮罩。

| 层 | 内容 |
|---|---|
| 底层 | `Image(directUrl)` —— CDN 直连缩略图，**挂载即发起**（不等可见性回调） |
| 上层 | 灰底 `Column`（宫格）/ 首字母占位 `Column`（头像）—— `directOk === false` 时盖住底层 |
| 判定 | `onComplete` 拿到尺寸：命中 **200×200 / 238×238** 判为贴吧占位模板 → **保持遮罩**（logo 永不上屏）；否则 `directOk = true` → 撤遮罩（这一帧即见真图） |
| 兜底 | `resolve` 照旧在视口门控下落地缓存（§4.1）；本地真图（`current`）优先级最高，一旦就绪直接盖掉直连 |

- 遮罩颜色与 `Image.alt()` 同色 → 观感是"灰底直接变真图"；
- 直连**不占闸门、不占我们的 rcp 会话**（走系统网络栈），所以它挂载即发不会把接口拖慢；
- 门控挂在**外层 `Stack`**（始终存在）上，撤遮罩不会把门控节点摘掉；
- 本地文件损坏（`Image.onError`）→ 回到"直连 + 遮罩"态并重启阶梯重试。

**代价**：受防盗链保护的少数图（直连必返占位）仍要等 `resolve` —— 与 v1.23 相同，但**只有这些图会等**；
另外直连与 `resolve` 会对同一张图各发一次请求（与原版行为一致，可接受）。
